# Devlog — 2026-08-15

## What got built

The session every prior one had been blocked waiting on: a real, funded key. Not from Anthropic —
that account stayed at a zero credit balance — but from AWS, which the user had real credits on. Given
a live Bedrock bearer token, verified it worked with a standalone `curl` against the real Bedrock
Converse REST endpoint (no app code involved) before touching anything, per explicit instruction: "we
will first verify it is working fine ... then only we will change anything in the code." First attempt
hit a real, documented AWS gate ("Model use case details have not been submitted for this account") —
a one-time Anthropic use-case form AWS requires per account, not a code or key problem; resolved
account-side, re-verified with the same curl, got back a real completion. Then built:

- **AWS Bedrock as a second `ChatModel` provider** — `HivemindLlmProperties` (new, the first
  `@ConfigurationProperties` record in this codebase — `ClaudeConfig` had grown past the "more than a
  couple of related `@Value` params" line this project treats as the signal to switch) and a rewritten
  `ClaudeConfig` that branches on `hivemind.llm.provider` (`anthropic`, default, unchanged behavior; or
  `bedrock`) to build either `AnthropicChatModel` or `BedrockChatModel`. Both implement LangChain4j's
  `ChatModel` interface, so `LlmClient`'s retry policy, cost tracking, and tracing span needed zero
  changes — the "one seam per external dependency" discipline paying off on exactly the case it exists
  for. Verified before writing code, not assumed: read the real 1.17.2 `langchain4j-bedrock` source
  (`BedrockChatModel`, `BedrockExceptionMapper`) and confirmed it maps 429/5xx/408 through the same
  `RetriableException` hierarchy every other provider uses. `BedrockChatModel.maxRetries(0)` keeps
  `LlmClient` as the single place a retry policy is configured, since Bedrock's client otherwise does
  its own internal retry by default.
- **`MarkdownCodeFenceStripper`** (new, `platform/llm/`) — a real bug, found the moment it became
  observable for the first time: `ClassifierAgent`'s first-ever real (non-auth-failing) completion
  failed to parse because Claude wrapped the requested JSON in a `` ```json `` fence despite the prompt
  saying "ONLY a JSON object, no prose." Every strict-JSON prompt in this codebase had been written and
  tested against mocks/scripts since session 2 — no session before this one had a real completion to
  test that assumption against. Fixed once, centrally, in `LlmClient.doChat()`; deliberately narrow
  (only strips a fence wrapping the *entire* response) so it doesn't risk silently mangling genuinely
  malformed output.
- **`TriageEvalToneJudge` + `TriageEvalToneJudgment`** (new, `verticals/triage/eval/`) — tone scoring
  (LLM-as-judge, 1–5), the one `docs/EVALS.md` scoring dimension that had sat designed-but-unbuilt since
  session 1 for lack of a real key to verify the judge call against. Split out of `TriageEvalScorer`
  specifically because it needs a real Claude call and every other dimension deliberately doesn't. A
  case with no drafted answer (skip-response or errored) gets no score at all, not a failing one.
  Judge cost is tracked separately from a case's production `costUsd` — it's eval-only overhead that
  never runs in production, and folding it into the cost-per-ticket gate would make that gate measure
  something it wasn't built to measure.
- **Wired tone through the whole reporting chain**: `TriageEvalResult` gained `toneScore`/
  `toneJudgeCostUsd`, `TriageEvalReport` gained `avgTone`/`toneScoredCases` (the latter so "zero
  applicable cases" can't be misread as "scored zero"), `TriageEvalRunner` calls the judge after
  scoring the rest of a case, and `TriageEvalHarnessRunner` finally reads `hivemind.eval.thresholds.
  tone-min-avg` — configured since the project's first session, unused until today — gating on it only
  when at least one case actually produced a score.

## Verified against reality, not just mocks

- `./mvnw test` — 64/64 green (up from 51): 3 new test classes (`ClaudeConfigTest`,
  `MarkdownCodeFenceStripperTest`, `TriageEvalToneJudgeTest`), plus new cases in `TriageEvalScorerTest`
  for tone-judgment threading.
- Real infra, real provider, real completions — the first time this has ever been true in this
  project's history. `docker compose up`, ran the actual Spring Boot app with
  `HIVEMIND_LLM_PROVIDER=bedrock`, POSTed a real ticket: `BILLING`, confidence 0.98, a genuine drafted
  answer citing `billing-duplicate-charge`, routed `AUTO_RESOLVE` — the pipeline's first-ever fully
  successful real run. Confirmed via the `llm.complete` trace span, not just the HTTP response:
  `llm.model="us.anthropic.claude-haiku-4-5-20251001-v1:0"`, real token counts, real cost
  ($0.000231 + $0.000887 for the two calls).
- Ran the full eval harness for real, twice: a cheap 2-case sanity check first
  (`--case=billing-001,abuse-001` — confirmed `avg tone 5.0 (1 scored)`, proving the skip-response case
  correctly contributed no tone score, not a bad one), then the full 73-case run. Primary set: 53/53
  passed all five gates — category/routing/citation accuracy 1.0, avg tone 4.32/5 (47 scored), p50/p95
  4.0s/5.2s, avg cost $0.00094/ticket. Adversarial set: 90% category accuracy, 80% citation recall, 1
  errored — `injection-004` (the model resisted a prompt-injection attempt correctly but appended
  prose after its JSON fence, which the deliberately-narrow stripper correctly left alone) and
  `contradiction-002` (a self-contradictory ticket landed on `OTHER` instead of `FEATURE_REQUEST`) are
  new findings; the four `nonenglish-*` citation misses confirm a limitation `docs/EVALS.md` had only
  predicted until today. Total real spend across both sets, every call included: $0.09. Tore down
  `docker compose` afterward.
