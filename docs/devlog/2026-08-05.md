## What got built

Real cost-per-ticket tracking, closing the fourth of the eval harness's five configured thresholds
(only tone scoring, which needs a live LLM-as-judge call, remains ungated).

- **`platform/llm/LlmResponse.java`** (new) — `{text, tokenUsage}`, what `LlmClient.complete()`
  actually returns now instead of a bare `String`. Verified the exact LangChain4j 1.17.2 API before
  writing any code: ran `javap` directly against `langchain4j-core-1.17.2.jar` already sitting in
  the local Maven cache rather than assuming method names —
  `ChatResponse.tokenUsage()` returns `TokenUsage`, which has `inputTokenCount()`/`outputTokenCount()`/
  `totalTokenCount()`, all boxed `Integer` (nullable).
- **`platform/llm/CostTracker.java`** (new) — turns a `TokenUsage` into a USD figure at a
  configurable per-million-token input/output rate (`hivemind.llm.pricing.*` in `application.yml`).
  The configured rates (`$3.00`/`$15.00` per million tokens) are explicitly labeled placeholders —
  commented in the YAML and in the class's own Javadoc — not verified published pricing for
  `hivemind.llm.model`. Didn't want to fabricate a specific dollar figure and present it as fact;
  the mechanism being real (real token counts → a real formula → a real gated threshold) is what
  matters here, not a number nobody verified.
- **`platform/agent/AgentResult.java`** — gained a `costUsd` field, added additively: the existing
  `success(payload)` and `failure(errorMessage)` factories still compile unchanged and now just
  default to `0.0`, so `RetrieverAgent` and `RoutingAgent` (neither calls an LLM) needed zero code
  changes. Only `ClassifierAgent`/`ResponderAgent` switched to a new `success(payload, costUsd)`
  overload.
- **`ClassifierAgent`/`ResponderAgent`** — both now unpack `LlmResponse.text()` (same as before) and
  additionally run `.tokenUsage()` through `CostTracker` to get a real dollar figure for that call.
- **Eval harness threaded through**: `TriageEvalRunner` sums `classifyResult.costUsd() +
  respondResult.costUsd()` per case (0.0 for whichever call never ran because an earlier stage
  failed first — `AgentResult.failure(...)` always carries 0.0), `TriageEvalResult`/`TriageEvalReport`
  gained `costUsd`/`avgCostUsd` fields, and `TriageEvalHarnessRunner` now gates on
  `cost-per-ticket-usd <= 0.05` alongside the three thresholds that were already live.
- **`LlmClient`'s own Javadoc got a small correction**: it previously said cost tracking could be
  "added here once without touching agent code." That turned out to be slightly optimistic — since
  the eval harness needs cost as real, aggregable, gate-able data (not just a log line), the number
  has to flow through the one place that sees an individual call's result, which is the agent itself.
  Updated the comment to reflect what was actually necessary rather than leave a now-inaccurate claim
  in place.

## Verified against reality, not just mocks

- `./mvnw test` — 43/43 green (up from 39): new `CostTrackerTest` (4 cases: input+output combined,
  null `TokenUsage`, null individual counts, zero tokens), plus updated `LlmClientTest`,
  `ClassifierAgentTest`, `ResponderAgentTest`, `TriageEvalScorerTest` for the new return types and
  parameters. The two agent tests now assert exact expected cost figures from real `TokenUsage`
  values (e.g. 100 input + 20 output tokens against $3/$15 per million = exactly $0.0006), not just
  that a cost field exists.
- Real infra: `docker compose up`, ran the actual harness
  (`ANTHROPIC_API_KEY=<dummy> ./mvnw spring-boot:run -Dspring-boot.run.profiles=eval`) against the
  real 53-case set. App booted cleanly with the new `CostTracker` bean and pricing config resolved.
  Log line and the written `eval-results/*.json` both correctly show `avgCostUsd: 0.0` — expected,
  since every case fails at the classify step on the dummy key before any tokens get billed, same
  constraint every session's manual verification has had. This proves the mechanism end-to-end
  (boots, runs, computes, gates, reports) without proving what a real non-zero number looks like —
  said plainly rather than glossed over, and now written into `INTERVIEW_PREP.md` as its own
  question so it doesn't get overclaimed later.
