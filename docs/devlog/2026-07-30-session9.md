## What got built

Real Postgres persistence, replacing the in-memory `TicketStatusStore` that's been an explicitly-
flagged placeholder since 2026-07-17. Ticket state now survives an app restart; it didn't before.

- **`db/migration/V1__create_tickets_table.sql`, `V2__create_audit_events_table.sql`** — Flyway
  migrations, run automatically on startup. Two tables, two different jobs: `tickets` is the
  current-state read model (one row per ticket, upserted in place — what `TicketStatusStore` used
  to hold), `audit_events` is immutable and append-only (one row per event ever published).
  Deliberately kept as two tables, not one — a mutable "what does this ticket look like right now"
  view and an immutable "what happened, in order" log are different concepts even though they're
  both about the same tickets.
- **`infra/persistence/TicketRepository.java`** — plain `JdbcTemplate`, not Spring Data JPA. The
  schema is one row per ticket with no relationships; JPA's entity lifecycle and lazy-loading
  machinery would be ceremony without payoff for something this simple. Same "thin explicit
  wrapper" shape as `EventBus`/`LlmClient`. Upserts via `ON CONFLICT (id) DO UPDATE`, hand-maps
  `ResultSet` rows back to `TriageResponse` (including `citedChunkIds` as a JSONB column,
  serialized/deserialized through the same `ObjectMapper` used everywhere else).
- **`platform/memory/AuditLog.java`** — vertical-agnostic (deals only in strings and JSON, same as
  `EventBus` not knowing what a "ticket" is), backed by `JdbcTemplate` too. One method: `append(
  vertical, entityId, eventType, payloadJson)`.
- **`EventBus.publish()` now writes to both Kafka and `AuditLog` in the same call.** This is the
  literal implementation of `ARCHITECTURE.md`'s "the event log is the audit log" line, which had
  been true only as a metaphor about Kafka topics until today — now every `eventBus.publish(...)`
  call really does produce one durable, queryable audit row, and the two can't drift out of sync
  because they're written by the same method, not two independently-maintained call sites.
- **`TicketStatusStore.java` deleted.** `TriageController` and all four consumers now depend on
  `TicketRepository` instead — a full replacement, not a second store running alongside the first.

## A necessary consequence: every `@SpringBootTest` now needs a real Postgres

Kafka's autoconfigured beans connect lazily — a `@SpringBootTest` without a real broker still
starts fine, it just can't actually send/receive. Flyway is the opposite: it connects and runs
migrations *eagerly* at context startup, so a missing database fails the whole Spring context, not
just the code path that touches it. That meant `HivemindApplicationTests`,
`ToolRegistrationIntegrationTest`, and `TriageKafkaIntegrationTest` — none of which cared about a
database before today — all needed one now, purely to start. Extracted
`AbstractPostgresIntegrationTest` (a shared `@Testcontainers` base with the Postgres container +
`@DynamicPropertySource` wiring) once a third test class needed the identical setup — same
discipline as every other extraction in this codebase, just applied to test infrastructure instead
of production code for the first time.

## Verified

- `./mvnw test` — **29 tests green** (same count as session 8 — no new test *classes*, but every
  existing `@SpringBootTest` now runs against a real ephemeral Postgres via Testcontainers instead
  of not needing one at all). `TriageKafkaIntegrationTest` gained two new assertions against
  Postgres directly (not just the HTTP view): the final `tickets` row has `status = 'routed'`, and
  `audit_events` has exactly 5 rows for that ticket — one per event the full pipeline run actually
  published (`ClassifyRequested`, `TicketClassified`, `TicketRetrieved`, `TicketResponded`,
  `TicketRouted`), proving `EventBus`'s dual write happened for real on every single stage, not just
  the ones with an obvious HTTP-visible effect.
- Manual verification against `docker-compose`'s real Kafka *and* Postgres (Flyway logs confirmed
  both migrations applied on a clean database): POSTed a ticket, confirmed the row in `tickets` and
  two rows in `audit_events` (`ClassifyRequested`, `TicketClassified` — the pipeline correctly
  stopped there since classification failed with the dummy key, so no retrieve/respond/route events
  exist for this ticket, exactly as designed) via direct `psql` queries, not just the API.
  - **The actual point of this session, demonstrated concretely**: killed the running app process
    entirely, started a fresh JVM against the same Postgres container, and `GET
    /api/v1/triage/tickets/{id}` for the *same ticket ID* returned identical data. The in-memory
    `TicketStatusStore` this replaced would have lost everything on that restart; this doesn't.
    Flyway's second startup log confirmed it validated the existing schema without re-running
    migrations — idempotent, as it should be.
  - Torn down cleanly afterward.
