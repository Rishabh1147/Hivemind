## Session 1

### What got built

Cost control for the eval harness ahead of actually getting a real Anthropic key — this is an
individual-budget project, not an org-funded one, so "don't burn money finding out the wiring works"
needed to be true before handing over real credentials, not figured out after the fact.

- **`hivemind.llm.model` now defaults to Claude Haiku 4.5**
  (`${HIVEMIND_LLM_MODEL:claude-haiku-4-5-20251001}` in `application.yml`), not Sonnet. Haiku is fully
  capable of exercising the pipeline and eval mechanics for dev purposes; override to a stronger
  model via the same env var for a run where response *quality* is actually what's being judged (a
  demo, an interview). Real cost math behind the decision: a full 73-case eval run (53 primary + 20
  adversarial, ~146 LLM calls) costs well under $1 even at Sonnet-shaped rates — the switch is about
  headroom and iteration speed more than avoiding a real budget problem.
- **`hivemind.llm.pricing.*` replaced with real, verified Claude Haiku 4.5 pricing** ($1/$5 per
  million input/output tokens, checked directly against `anthropic.com/claude/haiku`) — the first
  non-placeholder numbers here since `CostTracker` was built session 14. This wasn't the goal of the
  session, just a side effect worth calling out: switching the default model made the old $3/$15
  placeholder actively wrong for what's now configured, and looking up Haiku's real rate while making
  that change was strictly less work than leaving a stale placeholder in place. `hivemind.llm.model`
  and `hivemind.llm.pricing.*` aren't linked in code, though — a comment in `application.yml` flags
  that changing one without the other will quietly produce a wrong cost figure.
- **`TriageEvalRunner`/`TriageEvalHarnessRunner` gained a `--case=<id>[,<id>...]` filter** — the flag
  `docs/EVALS.md` has named since before the adversarial set even existed ("There's no per-case
  filter yet"), finally built. `TriageEvalRunner.run()`/`runAdversarial()` now take a
  `Set<String> caseIdFilter` (empty = run everything, the existing default behavior); filtering
  happens once, right after loading cases, before any agent runs — so a filtered case never reaches
  `ClassifierAgent`/`ResponderAgent` and never costs anything. Applies across both the primary and
  adversarial directories; an id with no match in one just runs zero cases there, which is harmless
  (zero cases means zero real calls, not an error).

### What got built: `PlannerAgent` — the pipeline's first real branching decision

User asked "can we do anything until the key comes, or should we pick something else — let's build
CodeScout" if not. Flagged a real tension before proceeding: starting a second vertical would
contradict this project's own stated sequencing ("CodeScout doesn't start until TriageBot is
genuinely done," written in `README.md`/`OVERVIEW.md`/`EXTENDING.md`), and TriageBot's own docs
repeatedly call the missing dynamic planner "the one honest structural gap" — jumping to CodeScout
now would mean leaving that gap open while starting something the project's own rules say waits for
it. Raised this via `AskUserQuestion` rather than silently picking a direction on a decision with
real project-narrative consequences; the user picked the planner.

- **`PlannerAgent`** (`verticals/triage/agents/`, new) — deterministic, no LLM call, same reasoning
  `RoutingAgent` already established for the final routing decision: whether to draft a response is a
  pure function of the classified category, and spending an LLM call to decide that would be the
  wrong trade (and, practically, unverifiable this session anyway with no funded key). Rule: `ABUSE`
  → `PlanDecision.SKIP_RESPONSE`, everything else → `DRAFT_RESPONSE`.
- **Threaded through the real pipeline, not bolted on**: `ClassifyRequestConsumer` calls
  `PlannerAgent` right after a successful classify and carries the decision as a new `nextStep` field
  on `TicketClassified`, unchanged through to `TicketRetrieved`. `TicketRetrievedConsumer` branches on
  it — `SKIP_RESPONSE` skips `ResponderAgent` (and its Claude call) entirely, publishing a
  `response_skipped` outcome with citations taken directly from what `RetrieverAgent` found (not
  LLM-filtered, since no LLM ran). Retrieval itself is never gated by the plan — the citation/audit
  trail survives even for a ticket that gets no drafted reply, which is what lets a gold-labeled
  `ABUSE` eval case still cite `abuse-policy` with nothing drafted.
- **`TriageResponse.withResponseSkipped(citedChunkIds)`** — a new `with*` method alongside
  `withResponse`/`withResponseFailure`, same progressive-enrichment shape the record already uses.
- **`TriageEvalRunner` mirrors the same branch** — calls `PlannerAgent` after classify, skips
  `ResponderAgent` on `SKIP_RESPONSE` exactly like the real consumer does, so scored cost and behavior
  reflect what production actually runs, not a stale always-call-every-agent shape.
- **Deliberately scoped narrow, and said so everywhere it's documented**: this doesn't decide
  retrieval, doesn't reorder stages, doesn't retry, and doesn't run at ingest (`TriageController`
  still publishes straight to `hivemind.triage.classify`, unchanged). "Four hardcoded Kafka hops" is
  no longer accurate for `ABUSE` tickets specifically; it's still accurate for every other category.

### Verified against reality, not just mocks

- `./mvnw test` — 51/51 green (48 + 2 new `PlannerAgentTest` methods + 1 new
  `TriageKafkaIntegrationTest` method). Caught and fixed a real test-isolation bug along the way: the
  new Kafka integration test initially made the *original*, unrelated test fail with "more than one
  record for topic found" on `hivemind.triage.routed`. Root cause — both tests read Kafka topics
  through the same deterministic `"test-<topic>-reader"` consumer group (derived from the topic name
  alone), and the new test hadn't drained `ROUTED` the way the original test does, so its message sat
  uncommitted and leaked into whichever test read that topic+group next. Fixed by draining every topic
  each test reads, matching the existing pattern, not by reaching for `@DirtiesContext`.
- Real infra, two-sided proof rather than trusting the final state: `RoutingAgent` escalates every
  `ABUSE` ticket unconditionally regardless of what got drafted, so "the ticket ended up escalated"
  can't by itself distinguish "the skip worked" from "a bug drafted a response anyway." Proved it two
  ways instead — `verify(responderAgent, never()).handle(any())` in the new integration test, and,
  against the real running app (`docker compose up`, dummy key), a direct trace comparison: a
  hand-published `ABUSE`-classified event produced a Kafka span sequence with **zero** `llm.complete`
  spans anywhere in it, while an otherwise-identical `BILLING`-classified event produced the usual one
  (still failing on the dummy key, but genuinely attempted). Also ran the eval harness itself with
  `--case=abuse-001,billing-001` against a real (if unfunded) key — both cases still fail at classify
  before reaching the planner branch at all, the same "can't observe a real success" limitation every
  feature has hit without a funded account; noted rather than glossed over. Tore down `docker compose`
  afterward.
