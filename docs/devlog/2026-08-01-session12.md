# Devlog — 2026-08-01 (session 12)

## What got built

Distributed tracing across the four-stage Kafka pipeline — the largest remaining deferred item
besides the dynamic planner, and the one most directly aligned with the production
Kafka/Spring/OTel background this whole project exists to demonstrate.

- **`pom.xml`** — added `io.micrometer:micrometer-tracing-bridge-otel` (bridges Spring Boot's
  Micrometer Observation API to the OpenTelemetry SDK) and `io.opentelemetry:opentelemetry-exporter-logging`
  (writes finished spans as log lines — no Jaeger/Zipkin container needed to see a trace end to end).
  Neither needs an explicit `<version>`; both are managed by `spring-boot-starter-parent`'s
  dependency management.
- **`infra/config/TracingConfig.java`** (new) — registers the `LoggingSpanExporter` bean. That's
  the entire wiring needed for Spring Boot to start exporting spans; everything else (HTTP request
  spans, the `Tracer`/`Propagator` beans) is autoconfigured once the bridge dependency is present.
- **`application.yml`** — `management.tracing.sampling.probability: 1.0`. Boot defaults to 10%;
  100% is the right call for a low-traffic demo where the point is showing a reviewer a trace, not
  managing collector volume — a real deployment would dial this down.
- **`EventBus.publish()`** — the producer-side seam. Opens a span named `kafka.publish <topic>`,
  child of whatever span is current on the calling thread, and injects it into the
  `ProducerRecord`'s headers via `Propagator.inject(...)` before sending. This is the exact seam
  the class's own Javadoc had been pointing at since 2026-07-30 ("OpenTelemetry span injection
  (roadmap) can be added here once").
- **`EventConsumer.consume()`** — the consumer-side seam. Extracts whatever trace context is on the
  incoming record's headers via `Propagator.extract(...)`, opens a `kafka.consume <EventType>` span
  as its child, and runs `onEvent` inside that span's scope. Constructor now takes `Tracer` and
  `Propagator` (same pass-through pattern the four consumer subclasses already used for
  `ObjectMapper`) — every subclass's constructor and `@KafkaListener` method signature updated to
  match, switching from consuming the raw JSON `String` to a `ConsumerRecord<String, String>` so the
  headers are actually reachable.
- **Why this closes the loop, not just each hop individually**: because `EventBus.publish()` always
  asks the tracer for "whatever span is current" as the parent, and `EventConsumer.consume()` always
  runs the agent inside the span it just extracted, a publish call made from *inside* a consumer's
  `onEvent` — which is exactly what every one of the four consumers does, to hand off to the next
  stage — automatically nests under that consumer's span. No trace id is ever passed as data through
  the event payloads themselves; the header injection/extraction at the Kafka boundary is the only
  place propagation happens, same as it would be for an HTTP-to-HTTP call.

## Verified against reality, not just mocks

- `./mvnw test` — still 35/35 green. The trace headers ride alongside the JSON payload without
  touching it, so `TriageKafkaIntegrationTest`'s `objectMapper.readValue(record.value(), ...)`
  reads were unaffected.
- Real infra: `docker compose up` (Kafka + Postgres), ran the app with a deliberately invalid
  `ANTHROPIC_API_KEY` (same constraint as every prior session — no real key available to verify a
  passing run against), `POST`ed one ticket, and grepped the `LoggingSpanExporter` log output.
  Five spans came back sharing **one trace id** (`b1805841324140f21b9a05a97f5d6a02`):
  `http post /api/v1/triage/tickets` (SERVER, autoconfigured — no code written for this one) →
  `kafka.publish hivemind.triage.classify` → `kafka.consume ClassifyRequested` →
  `kafka.publish hivemind.triage.classified` → `kafka.consume TicketClassified`. The chain stops
  there because classification genuinely failed (`invalid x-api-key`, a real Anthropic auth error)
  and `TicketClassifiedConsumer` correctly skips retrieval for a failed classification — the same
  behavior every previous session's dummy-key runs have shown, just now with a trace id tying the
  whole thing together. `GET /tickets/{id}` confirmed `status: "classification_failed"` with the
  real error message attached.
- Also confirmed the negative case makes sense: none of the spans carry an `exception` tag, because
  `ClassifierAgent`'s failure is returned as an `AgentResult` (failure-as-data, the codebase's
  standing rule), never thrown — so `EventConsumer`'s `catch (Exception e) { span.error(e); }` branch
  correctly never fires here. A real code bug that threw instead of returning `AgentResult.failure`
  would show up as a red-flagged span, which is itself a useful property.
- Full 4-stage trace continuity (through retrieve/respond/route) is verified by code inspection —
  the propagation mechanism is identical at every hop, proven for real at the first two — but not
  by an actual end-to-end run, since that needs a working Claude key this session didn't have.
  Worth re-running this same check once a real key is available, purely to see the whole trace.
