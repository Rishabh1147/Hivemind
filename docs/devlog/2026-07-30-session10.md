## What got built

The eval harness — `docs/EVALS.md`'s design, unbuilt since the project's first commit, finally has
running code and a real (if small) case set behind it. `hivemind.eval.thresholds.*`, configured but
unread since day one, are now actually enforced.

- **`verticals/triage/eval/{TriageEvalCase, TriageEvalResult, TriageEvalReport}.java`** — the data
  shapes. `TriageEvalCase` deliberately deviates from `EVALS.md`'s original `snake_case` sketch
  (`must_cite` → `mustCite`) to match Java naming — the design doc predates implementation, and this
  was a conscious small adjustment, not a miss.
- **`verticals/triage/eval/TriageEvalScorer.java`** — pure comparison logic (category match, routing
  match, citation recall), extracted into its own class specifically so it's unit-testable without
  running any agent — 6 tests, no mocks, no I/O.
- **`verticals/triage/eval/TriageEvalRunner.java`** — loads every `evals/triage/*.json` case and
  runs it through `ClassifierAgent` → `RetrieverAgent` → `ResponderAgent` → `RoutingAgent` directly
  and sequentially, not through Kafka. Deliberate: evals are a batch quality-scoring loop over model
  decisions, not a re-verification of event-bus plumbing (`TriageKafkaIntegrationTest` already
  covers that) — going through Kafka for 50+ cases would add async polling latency and flakiness to
  a job that should be fast and repeatable.
- **`verticals/triage/eval/TriageEvalHarnessRunner.java`** — a `CommandLineRunner` gated behind
  `@Profile("eval")`, invoked via `--spring.profiles.active=eval`. Writes the report to
  `eval-results/<timestamp>.json` (already gitignored — this directory has been described in docs
  since session 1) and gates on `category-accuracy`, `citation-recall`, and `p95-latency-ms` from
  `application.yml`. Deliberately does **not** gate on `tone-min-avg` (needs an LLM-as-judge call
  this session had no live Anthropic key to verify) or `cost-per-ticket-usd` (needs the not-yet-built
  `CostTracker`) — both configured values stay unused rather than gated on numbers that were never
  actually measured.
- **`evals/triage/*.json`** — 10 hand-written cases (4 billing, 3 bug, 1 feature request, 1 abuse,
  1 other), well short of `EVALS.md`'s 50+ target but a real, working starter set with genuine
  category/citation coverage. Ticket wording was deliberately chosen to reuse exact word forms from
  the target `KnowledgeBase` chunks — `SearchKbTool`'s naive keyword-overlap scorer (2026-07-20) has
  no stemming, so "payment" and "payments" are different tokens to it; writing cases that ignore
  that would silently under-test citation recall.
- **`expectedRouting` is nullable, and usually null.** `EVALS.md`'s schema treats routing as always
  assertable, but in practice it depends on model confidence, which isn't knowable when a human
  authors a case — only the `ABUSE` case asserts `ESCALATE`, since that branch of `RoutingAgent`'s
  policy doesn't depend on confidence at all. A null `expectedRouting` scores as "not applicable,"
  not "must be null."

## A real bug, caught by actually checking the exit code

`TriageEvalHarnessRunner` originally called `SpringApplication.exit(applicationContext, () -> passed
? 0 : 1)` and stopped there. Running it against the dummy key correctly logged `Eval run FAILED
gating thresholds` — but the process exit code was **0** regardless, which would have silently let a
failing eval run pass a CI gate. `SpringApplication.exit(...)` only *computes* an exit code and
closes the context; it doesn't call `System.exit(...)`. Wrapping it —
`System.exit(SpringApplication.exit(...))` — fixed it. Caught by literally checking `$?` after
running the packaged jar directly (`java -jar target/hivemind-*.jar
--spring.profiles.active=eval`), not by reading the code or trusting the log line looked right —
consistent with this project's whole verification ethos, and a genuinely easy mistake to make
silently, since the log output looks identical either way.

## Verified

- `./mvnw test` — **35 tests green**, up from 29: 6 new `TriageEvalScorerTest` cases (perfect match,
  wrong category/routing, null-expected-routing-is-not-a-failure, citation recall met/unmet/vacuous).
  The eval harness itself doesn't run during `mvn test` — it's gated behind the `eval` Spring
  profile, which the default test run never activates, so it can't accidentally slow down or flake
  the normal suite.
- Manual run against real infrastructure: started `docker-compose` (Postgres required — Flyway still
  runs eagerly at startup regardless of profile; Kafka not actually used by the eval path but kept
  running for consistency), ran the packaged jar with `--spring.profiles.active=eval` and a
  deliberately-invalid Anthropic key. All 10 cases correctly errored at the classify step (real auth
  failures, same as every other session's dummy-key verification), producing `categoryAccuracy: 0.0`
  — exactly the outcome a genuinely broken pipeline should produce. Confirmed the report JSON
  (`eval-results/<timestamp>.json`) contains real per-case latencies and the real Anthropic error
  message per case, then confirmed — after the `System.exit` fix — that the process exit code was
  **1**, matching the logged gating failure. This is itself the desired behavior verified: **the
  harness correctly identifies and reports a failing pipeline**, which is precisely what a CI gate
  needs to do, even without a real key to demonstrate a passing run.
- Cleaned up (`eval-results/*.json` removed, `docker compose down`) — the report files are
  gitignored and shouldn't linger locally as stale artifacts either.
