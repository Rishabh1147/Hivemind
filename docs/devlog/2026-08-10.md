# Devlog — 2026-08-10

## What got built

The 20-case adversarial eval set from `docs/EVALS.md` — flagged as a next-session candidate since
2026-08-03, deferred three times behind higher-priority work (cost tracking, tracing spans, the
Jaeger backend). No live Anthropic key available this session either (checked, still empty), so this
was picked as the most valuable candidate that doesn't need one — same reasoning that picked it over
tone scoring every prior session it was considered.

- **`evals/triage-adversarial/`** (new, 20 cases) — 4 cases each across the 5 sub-categories
  `EVALS.md` names: prompt injection (one per real category, testing whether the classifier ignores
  an embedded instruction rather than obeying it), contradictory ticket content, multi-issue tickets,
  non-English text (French/German/Hindi/Portuguese, deliberately *without* the inline English
  translation the primary set's `edge-002` uses — a genuine stress test of raw foreign-language
  input, not a cushioned one), and no-relevant-KB-context grounding checks (`mustCite: []`).
  Same `TriageEvalCase` schema as the primary 53-case set — no new fields needed.
- **Deliberate, documented deviation: "contradictory KB entries" adapted to "contradictory ticket
  content."** The original sketch meant planting a real contradiction inside `KnowledgeBase`, but
  that KB is shared with all 53 primary cases' citation-recall scoring via naive keyword-overlap —
  adding a contradiction there risked shifting retrieval results for cases that have nothing to do
  with the adversarial set. Adapted to tickets that contradict themselves or contradict what a real
  KB chunk actually says instead, and wrote the reasoning directly into `EVALS.md` rather than
  building something narrower than the doc describes and leaving it unexplained.
- **`TriageEvalRunner`** — refactored `run()` into a directory-parameterized `runDirectory(Path)`,
  with `run()` (primary, unchanged behavior) and a new `runAdversarial()` both delegating to it. No
  duplicated loading/scoring/aggregation logic between the two sets.
- **`TriageEvalHarnessRunner`** — now also calls `runAdversarial()` and writes its report to
  `eval-results/<timestamp>-adversarial.json`, logged separately ("not gated, tracked only"). The
  gating `passed` boolean is computed from the primary report *before* the adversarial run even
  starts — structurally, not just by convention, there's no code path where adversarial results could
  affect the exit code.
- **`AdversarialEvalCaseSetTest`** (new, 5 tests) — same structural checks as the existing
  `EvalCaseSetTest` (unique ids, real `mustCite` chunk references, non-blank tickets), plus one the
  primary test doesn't need: no id collisions between the two case sets.

## Verified against reality, not just mocks

- `./mvnw test` — 48/48 green (up from 43): the 5 new `AdversarialEvalCaseSetTest` methods, no
  changes needed to any other test.
- Real infra: `docker compose up`, ran the actual harness
  (`ANTHROPIC_API_KEY=<dummy> ./mvnw spring-boot:run -Dspring-boot.run.profiles=eval`). Both report
  files were written — `eval-results/<timestamp>.json` (53 cases, 53 errored, same dummy-key failure
  every session's manual verification has hit) and `eval-results/<timestamp>-adversarial.json` (20
  cases, 20 errored, same reason) — confirmed by inspecting both files directly, not just the log
  output. The adversarial run logged as `Adversarial eval run complete (not gated, tracked only):
  20 cases (20 errored)...` and the process exit code was `1`, matching only the primary report's
  gating failure. Spot-checked the adversarial report's case ids against what was actually written to
  disk — all 20 present, no truncation. Tore down `docker compose` afterward.
