## Session 1: tool-call spans on `ToolInvoker`

Closed the other half of the observability gap flagged since session 12 ("LLM-call and tool-call
spans aren't instrumented yet") — LLM spans landed 2026-08-06, tool spans land now.

- **`platform/tool/ToolInvoker.java`** — `invoke(toolName, operation)` now opens one `tool.invoke`
  span per logical call, covering every retry attempt underneath it — the identical
  one-span-per-operation choice `LlmClient.complete()` made two sessions ago, not a new pattern.
  Tags `tool.name`, `tool.success`, and `tool.retry_count` (attempts beyond the first). No
  `span.error(...)` anywhere in this class, deliberately: `invoke()` never throws — every failure,
  including one the tool itself threw, comes back as `ToolResult.failure(...)` (the same
  failure-as-data idiom as `AgentResult`), so there's no exception that ever escapes the span's scope
  to mark. Retry count is threaded out of the retry loop via a small private `Attempt<T>` record
  rather than scattering `span.tag(...)` calls across four different catch blocks.
- No `tool.vertical` tag, same reasoning as `llm.vertical` from 2026-08-06: nothing plumbs a vertical
  into `ToolInvoker` today, and only one vertical calls in.
- `ToolInvoker` gained `Tracer` as a constructor dependency (same as `LlmClient`). Updated the three
  call sites that construct it directly in tests (`ToolInvokerTest`, `RetrieverAgentTest`) to pass
  `Tracer.NOOP` — a real no-op implementation, not a mock, matching how `LlmClientTest` already
  handled this.

**Verified against reality, not just mocks:**
- `./mvnw test` — 43/43 green, same count (no new test methods; existing tests updated for the new
  constructor parameter).
- Real infra, and a stronger check than the LLM span session got: `docker compose up`, booted the
  real app, then hand-published a `TicketClassified` event straight onto
  `hivemind.triage.classified` via `kafka-console-producer.sh` (the isolation trick used since
  session 3 to exercise one consumer without needing a working `ANTHROPIC_API_KEY`) — this drives
  `RetrieverAgent` → `ToolInvoker.invoke("searchKb", ...)` directly, and `searchKb` needs no LLM key
  at all. Grepped the log-exported spans and got a real *successful* invocation, not just a
  forced-failure path:
  `'tool.invoke searchKb' : b517fff5ea616abf6473d91fb157b0b3 ... {tool.name="searchKb",
  tool.retry_count="0", tool.success="true"}` — nested under the same trace id as the surrounding
  `kafka.consume`/`kafka.publish` spans, and the trace continued on through the responder and router
  stages too. Tore down the app and `docker compose` afterward.

## Session 2: real Jaeger backend over OTLP

Every span type `ARCHITECTURE.md` names (HTTP, Kafka, LLM, tool) existed by the end of session 1
today, which made this the natural next move — closes the "OTLP exporter to a real backend" item
that's been sitting on the "what's next" list since session 12 (2026-08-01).

- **`docker-compose.yml`** — added a `jaegertracing/all-in-one:1.62.0` service (`COLLECTOR_OTLP_ENABLED:
  "true"`), publishing the Jaeger UI (`16686`) and its OTLP HTTP receiver (`4318`) to the host.
- **`pom.xml`** — added `io.opentelemetry:opentelemetry-exporter-otlp` (no explicit version; managed
  by Spring Boot's `opentelemetry-bom` import, same as the existing `opentelemetry-exporter-logging`
  dependency). Confirmed via `javap`/inspecting the actual jar that the artifact really does contain
  `OtlpHttpSpanExporter` before trusting the dependency name from memory — same "verify against the
  real jar" habit as session 14's `CostTracker` work.
- **`application.yml`** — `management.otlp.tracing.endpoint` set to Jaeger's OTLP HTTP endpoint
  (`http://localhost:4318/v1/traces`, overridable via `HIVEMIND_OTLP_ENDPOINT`). This alone is enough
  for Spring Boot Actuator's `OtlpAutoConfiguration` to register an `OtlpHttpSpanExporter` bean — no
  new `@Bean` method needed anywhere.
- **Deliberately not a swap.** `TracingConfig`'s existing `LoggingSpanExporter` bean stays registered:
  Spring Boot composes every `SpanExporter` bean present in the context into one composite exporter,
  so both fire on every span. `./mvnw test` and any local run without `docker compose up` still get
  spans as log lines with zero extra infra; the full stack additionally gets them in a real,
  browsable trace store. Confirmed this composition assumption is actually how Spring Boot behaves
  (found `SpanExporters`/`SpanProcessors` in `spring-boot-actuator-autoconfigure`, which multiplex
  multiple exporter beans) rather than assuming it and finding out one exporter silently won.

**Verified against reality, not just config:**
- `./mvnw test` — 43/43 still green with the new dependency + property in place, no test disruption.
  When Jaeger isn't running (true for every existing test), the OTLP export just fails quietly per
  batch — OTel's span processor is async, so a failed export never surfaces as a test failure or an
  app-level error. Confirmed no `OtlpHttpSpanExporter`/export-failure noise even appeared in the test
  log within a normal test run's short lifetime.
- Real infra, verified against Jaeger's own REST API rather than trusting the config was spelled
  right: `docker compose up` (now including Jaeger), booted the app, POSTed a ticket.
  `curl http://localhost:16686/api/services` → `["jaeger-all-in-one", "hivemind"]` — proof `hivemind`
  was actually registering traces, not just that the container was up.
  `curl http://localhost:16686/api/traces?service=hivemind` returned the full trace as JSON: the same
  six spans the log-line verification has always shown (HTTP POST, 2× Kafka publish, 2× Kafka
  consume, `llm.complete`), now round-tripped through a real OTLP export into a real trace store. The
  `llm.complete` span's real Anthropic auth failure came through automatically as
  `otel.status_code=ERROR` with the actual `invalid x-api-key` message in `otel.status_description` —
  Jaeger surfacing the `span.error(e)` call already in `LlmClient` from session 15, no new code
  needed for that to show up. Re-ran session 1's hand-published-Kafka-event trick and confirmed
  `tool.invoke searchKb` landed in Jaeger too, tags and all. Tore down the app and `docker compose`
  afterward.
